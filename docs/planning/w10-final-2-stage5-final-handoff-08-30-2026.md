## 1. Preparation from a clean disposable environment

Commands only — no output reproduced here beyond what's needed to show the
preparation is deterministic and documented:

```bash
git fetch origin && git checkout c15f0638726d452ddd2964343d6095e05af907ad
cp .env.example .env   # only if .env doesn't already exist locally
```

Four variables the committed `.env` does not supply on a clean checkout
must be exported to the shell only (never written to `.env`) before
`make up`/`make demo-reset` will succeed: `DB_ADMIN_PASSWORD`,
`PHI_ACTIVE_KEY_VERSION`, `PHI_ENCRYPTION_KEY_V1`, `PHI_BLIND_INDEX_KEY_V1`.
Generate fresh ephemeral values per `docs/runbook.md`'s own guidance
(`openssl rand -hex 32` / `openssl rand -base64 32`), export them in the
same shell session, then:

```bash
make up            # docker compose up -d
make seed          # schema + demo data into the running Postgres
make demo-reset    # reusable reset to the four canonical patients' baseline
```

`make rag-prepare` (`db/policy_corpus_prepare.py` inside records-service)
was also run as part of preparation, per standing practice. It failed with
a real `botocore.errorfactory.AccessDeniedException: ... Authentication
failed: Please make sure your API Key is valid.` — the `.env`'s configured
`AWS_BEARER_TOKEN_BEDROCK` is invalid on this environment. This is a
credential-provisioning gap, not a code defect (`db/policy_corpus_prepare.py`
correctly validated config presence, attempted the call, and failed
loudly rather than silently) — recorded truthfully in §3 below, not
treated as a rehearsal blocker.

`make demo-reset`'s own verification output after each reset (both runs
below) confirmed the documented baseline: patients 1042/1737 have no
portal account (invite-ready); 1738/1739 have a fixed demo password
(`portalportal123`, `PATIENT_DEMO_PASSWORD`); all four have their seeded
coverage/encounters/records/appointments/thread state and zero pending
ROI requests.

## 4. Expected screen/API sequence for a live walkthrough

1. Log in as `frontdesk` or `drkim`.
2. Open the patient's chart (`/patients/{id}/records` in the API; the
   frontend's Records page for a browser walkthrough).
3. As `drkim`, request/observe the patient summary review queue and
   approve the pending case.
4. As the patient, view `/patient/me/summary` before and after approval —
   the approved item's `released_by_review` flag and real quote should be
   visible in the response/UI.
5. As `frontdesk`, verify coverage (expect the simulated-response banner,
   not a real payer round trip) and book an appointment.
6. As `drkim`, post a message on the patient's seeded thread.
7. As `frontdesk`, run the ROI request → authorization → review → fulfill
   sequence; confirm the reviewed authorization shows the actual logged-in
   reviewer, not any client-supplied name.

## 5. Limitations

- **RAG corpus was never successfully ingested on this environment** — the
  configured Bedrock credential is invalid (`AccessDeniedException`), so
  `agent-draft` refuses for lack of approved source material and
  `policy/ask` falls back for lack of a reachable model. This is an
  environment/credential-provisioning gap, not a runtime code defect —
  provisioning a valid Bedrock-authorized credential for this environment
  is an infrastructure/account decision, out of this stage's scope.
- This remains a synthetic training/demo environment: no production data,
  no HIPAA certification, no TLS on any hop, no disk/volume-level
  encryption, and only selected PHI fields are application-encrypted (see
  `CLAUDE.md`'s Known Risks / Debt section for the exact, current, field-
  by-field list — do not describe this system as having encrypted PHI
  without naming which fields).
- `eligibility-service`, `scheduling-service`, `interop-service`, and
  `roi-service` still have no gateway-to-service internal-token check
  (only `intake-service`/`records-service` do) — unrelated to this
  rehearsal, unchanged by this PR.

## 6. Recovery / reset steps

- Between any two rehearsals, or if a rehearsal leaves inconsistent state:
  `make demo-reset` restores all four canonical patients to their
  documented baseline (verified by its own printed verification table —
  see §1) without touching immutable audit history or requiring a fresh
  volume.
- To rebuild from nothing: `docker compose down -v --remove-orphans` (tear
  down containers and volumes) then repeat §1's preparation sequence from
  `make up`.
- If `make up`/`make demo-reset` fails with a `required variable ... is
  missing a value` error, the four ephemeral variables in §1 were not
  exported in the current shell session — re-export them; they are never
  persisted to `.env` and do not survive a new shell.
